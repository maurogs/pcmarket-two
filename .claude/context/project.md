# Project Context

## Overview
PCMarket is a Rails 8.1 marketplace for buying and selling PC parts. This document tracks architectural decisions, the current code map and open items.

## Stack
- Ruby 4.0.9, Rails 8.1.4, PostgreSQL
- Propshaft asset pipeline, importmap, Hotwire
- Tailwind CSS via `tailwindcss-rails` (source in `app/assets/tailwind/application.css`, compiled to `app/assets/builds/tailwind.css`)
- I18n with six locales: es (default), en, fr, de, it, pt
- Devise + devise-i18n, OmniAuth Google, Pundit, Pagy, pg_search, FriendlyId, MetaTags, SitemapGenerator, Flipper, Mobility, AASM, Stripe, Rack::Attack, ActiveStorageValidations
- i18n-tasks and Faker in development/test; letter_opener_web in development

## Decisions
- Spanish is the default locale; the fallback chain is English then Spanish (`config.i18n.fallbacks = [ :en, :es ]`), also used by Mobility.
- Time zone is `Madrid`.
- English copy uses British spelling (en-GB): colour, favourites, basket.
- All user-facing strings live in `config/locales/*.yml` with an identical nested key structure rooted at each language code.
- Locale is detected in `app/controllers/concerns/localization.rb` with this priority: `params[:locale]`, `cookies[:locale]`, `Accept-Language`, `I18n.default_locale`; validation uses `I18n.available_locales` (the old `SUPPORTED_LOCALES` constant was removed in Phase 0b).
- The chosen locale is persisted in `cookies[:locale]` for one year.
- HTML routes live under an optional locale scope `scope "(:locale)", locale: /es|en|fr|de|it|pt/`; the health check and OmniAuth callbacks stay outside it.
- `locale.names.*` keys are referenced dynamically by the locale switcher and are explicitly ignored by i18n-tasks. `nav.categories.*`, `countries.*`, `settings.*`, `devise.failure.*` and `activerecord.*` are ignored for the same reason (dynamic lookups, admin UI and Devise runtime resolution).
- Design tokens live in `app/assets/tailwind/application.css` under `@theme`: primary (indigo/violet, 50–900), accent (warm coral), semantic surface/canvas/content/muted/border, success/warning/danger, and radius/font tokens. Inter is loaded from Google Fonts with `display=swap`.
- Dark mode uses the class strategy (`@custom-variant dark (&:where(.dark, .dark *))`); `.dark` overrides the same semantic CSS variables, so no `dark:` variant is needed for surfaces. An inline script in `<head>` applies the stored/system theme before paint to avoid a flash.
- The shell is split into `app/views/shared/` partials: `_announcement_bar`, `_header`, `_main_nav`, `_footer`, `_flash`, `_back_to_top`, plus `_search_form`. Desktop and drawer navigation share `_main_nav` via a `mobile` local.
- Stimulus controllers in `app/javascript/controllers/`: `theme`, `drawer`, `dropdown` and `flash`. The mobile drawer is an off-canvas dialog with Escape/scroll-lock handling; the dropdown is a reusable accessible menu.
- Tailwind is linked through `stylesheet_link_tag :app`, which includes all CSS under `app/assets` (application.css and the compiled tailwind.css).
- The Tailwind watcher runs as `tailwindcss:watch[always]` in `Procfile.dev` so it stays alive when stdin is closed (non-interactive shells/CI).
- Flipper uses the ActiveRecord adapter (`config/initializers/flipper.rb`); its `flipper_features` and `flipper_gates` tables are created by `db/migrate/20261112085830_create_flipper_tables.rb`. The UI is mounted at `/admin/flipper` behind `authenticate :user, ->(user) { user.admin? }`.
- Authentication is Devise with database_authenticatable, registerable, recoverable, rememberable, validatable, confirmable, lockable, trackable and omniauthable (google_oauth2).
- `username` is a `citext` column with a unique index, 3–30 characters and `[a-zA-Z0-9_-]`; it is required at registration (no auto-suggestion).
- `User#active_for_authentication?` returns false for banned (`banned_at`) and soft-deleted (`deleted_at`) accounts; `inactive_message` returns `:banned` or `:deleted` with translations in `devise.failure.*`.
- Google OAuth is registered only when both the client id and secret exist in credentials (`google.client_id`/`google.client_secret`) or `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`. The login button and OAuth routes are absent otherwise.
- OmniAuth callbacks live outside the locale scope. User creation/linking is isolated in `Users::FromOmniauth`; existing emails are linked to the Google identity, new users are confirmed and get a generated unique username.
- Devise controllers inherit `ApplicationController` (`config.parent_controller`) so auth pages use the locale switch, Pundit, `allow_browser` and the application layout.
- Devise views use a shared two-column card partial (`devise/shared/_auth_layout.html.erb`): brand/benefits on the left, form on the right, using the existing Tailwind component classes. Devise strings come from devise-i18n.
- Registration requires accepting the terms (virtual `terms_accepted`, persisted as `terms_accepted_at`); marketing opt-in is optional.
- Pundit is included in `ApplicationController`. `Pundit::NotAuthorizedError` redirects back with a translated alert for HTML and returns 403 JSON for JSON requests.
- Stores are one-per-user seller storefronts with FriendlyId slugs and slug history. Business stores require `tax_id`. Counter/rating columns are denormalised on the store row.
- Countries are catalogue rows with ISO2 codes, VAT, currency and launch state. Names are resolved from `countries.*` translations. `Country.launched_codes` is cached and invalidated after commit.
- Regions belong to countries through the string `country_code` FK and are unique per `[country_code, code]`. The seeds include the 52 Spanish provinces plus the top-level regions for FR, GB, DE, IT and PT; GB carries the four nations and can bulk-import counties.
- Settings are admin-tunable JSONB values with a declared `value_type`. `Setting.get` caches typed values in `Rails.cache`; `Setting.set` infers the type and both invalidate the cache after commit.
- Seeds are split into `db/seeds/countries.rb`, `regions.rb`, `settings.rb`, `features.rb`, `categories.rb`, `attributes.rb` and `tags.rb`, loaded from `db/seeds.rb`; all are idempotent. New features start disabled without resetting existing flags, ES is the only launched country, and the confirmed admin comes from `ADMIN_PASSWORD` or `ChangeMe123!`.
- Catalogue seeds use `find_or_initialize_by` + `assign_attributes` + `save!` and local variables (no constants) so repeated loads in tests are silent. The tree has 51 categories (10 roots + 41 children), 45 attribute definitions with 428 options, and 34 tags (13 product labels + 21 seller tags). Generic option labels and tag names are translated in all six locales; brands, model names, numbers and acronyms are identical by design. Physical leaf categories automatically receive `warranty_months` and `includes_original_box`, except Games, Software and the accessory leaves other than Collectibles. Stale `CategoryAttribute` links are pruned on each run.
- Test helper injects a modern Chrome User-Agent for all integration requests (needed by `allow_browser versions: :modern`) and includes `Devise::Test::IntegrationHelpers`.
- Mobility uses the `jsonb` backend with reader/writer/query/fallbacks/presence plugins and locale accessors for all six locales; `config.i18n.fallbacks = [:en, :es]` gives the English → Spanish fallback chain. Translated catalogue columns are `jsonb NOT NULL DEFAULT '{}'`.
- `listings.searchable` is a **stored generated tsvector column** (not a trigger) so `db/schema.rb` can reproduce it. It combines title (A), `specs::text` (B) and description (C) with the `simple` config and an immutable `translate(lower(...))` accent fold; `pg_search` applies `unaccent` to the query. `pg_trgm` and `unaccent` are enabled by migration.
- Google identities are linked to existing accounts only when Google reports the email verified (`extra.raw_info.email_verified` or `info.email_verified`); otherwise the callback redirects to sign-in with a translated alert.
- Listing status is an AASM state machine on a plain string column; `Setting.get(:listings_require_approval)` decides whether submit/republish publish directly. Material edits (title/description/specs/category/photos) reset a published listing to `pending_review`; price/quantity/shipping edits do not.
- `Store#listings_count` and `Category#listings_count` are maintained by Listing `after_commit` callbacks that compare before/after `(store_id, category_id, published?)` tuples — no plain `counter_cache`.
- Category tree queries use recursive CTEs (`UNION` dedup for cycle safety); `descendant_ids` is cached with a key containing `Category.maximum(:updated_at)` and `belongs_to :parent, touch: true` propagates touches.
- `Category#effective_attribute_definitions` preloads `attribute_definition: :attribute_options` in one query.
- `Listing.with_specs` uses only jsonb containment predicates (`specs @> ?::jsonb` for the scalar and array forms of each value), so the `jsonb_path_ops` GIN index on `specs` is used; it ORs values within a key and ANDs across keys.
- Public browsing routes live inside the locale scope: categories at `/c/:slug`, listings at `/l/:slug` and search at `/search`. Category and Listing use FriendlyId `history`, so old slugs are found and 301-redirected to the current slug.
- `ListingSearch` (app/queries) owns all public listing querying and returns a result struct with Pagy records, total count, facets, applied filters and the active filter metadata. It starts from `Listing.visible`, ignores invalid numbers/params and only accepts spec keys that belong to the current category's effective filterable attributes.
- Facet and condition counts are one SQL round trip over a materialised filtered CTE using `jsonb_each`/`jsonb_array_elements_text`; counts include the attribute's own filter (zero-result options are disabled) and are cached for 5 minutes under a normalized key plus `listings/version`. `Listing` writes that version key after every commit.
- Result pages share one template. Filters submit as GET inside a Turbo frame with `data-turbo-action="advance"`; Stimulus auto-submits checkboxes and debounces text/price input (400 ms), while a `<noscript>` path keeps the form usable without JavaScript. Cards use `card` variants, eager loading for the first four, and Russian-doll fragment caching keyed by listing, locale and eager state.
- The main navigation is built from `Category.active` (one query), cached as rendered HTML per locale and mobile/desktop variant with `Category.tree_cache_version` (the maximum `updated_at`) in the key.
- Listing detail visibility is published + active store + active seller, with owners, admins and moderators able to inspect non-public listings and see a status banner. Anonymous detail responses use `fresh_when` with `[listing, locale, user id]`; anonymous category/search responses send `Cache-Control: max-age=60, public`.
- View counts increment with `update_column`, throttled by a per-listing session key. `DeliveryEstimate` counts handling days and the 2–4 day carrier window in business days, skipping weekends and starting on the next business day for weekend orders.
- SEO uses the MetaTags gem for title/description/OG/Twitter defaults and per-page overrides, hreflang alternates for all six locales plus x-default, BreadcrumbList/ItemList/Product+Offer JSON-LD, canonical URLs and `noindex,follow` on filtered or sorted result URLs. Page 2+ result URLs canonicalise to themselves.
- Active Storage variants use `:mini_magick` (ImageMagick is available; libvips is not), with `card`, `large` and `thumb` variants for listing photos.
- Store onboarding is a singular `/store` resource (`new/create/edit/update`). Users without a store are redirected there before listing an item. `stores.region_id` links the selected Spanish province; `province` is kept in sync with the region name.
- Spanish NIF/NIE/CIF numbers are validated by `SpanishTaxIdValidator` (control letters/digits, tolerant of spaces, dots and hyphens). `Store` validates the tax ID globally and requires region/city (plus a five-digit postal code for business stores) in the `:onboarding` context.
- Business sellers' legal name, tax ID and address are rendered in the public seller card on listing pages, matching the EU DSA trader-transparency notice in the store form.
- The seller listing flow is `/sell` (`Sell::ListingsController`, RESTful index/new/create/edit/update/destroy; named `sell_listings` to avoid clashing with the public `listings` routes). Step 1 creates the draft; later steps PATCH `update` with a `step` parameter inside the `listing_wizard` Turbo frame.
- Wizard steps are `category`, `photos`, `details`, `price` and `review`. `Listing` uses those names as validation contexts; title/description/price/handling/quantity validations are skipped in earlier contexts so a draft can exist before those fields are filled. `title`, `description` and `price_cents` are nullable at database level until the matching step fills them.
- `Listings::SaveStep` persists attributes, photo uploads/removals/order and saves with the step context. `Listings::Submit` validates the `:review` context, calls the AASM `submit` event and has a TODO hook for the future moderator notification.
- Photo uploads use Active Storage direct uploads (`@rails/activestorage`), the `sortable` Stimulus controller (native HTML5 drag plus up/down buttons) and the `category_picker`, `character_counter` and `store_kind` helpers. The photo limit comes from `Setting.get(:max_images_per_listing)`, and type/size errors are translated.
- Sellers can select only seller tags (max 5) through `seller_tag_ids`; product labels remain an admin-only assignment. The offers toggle appears only when the `:offers` Flipper flag is enabled and defaults to `store.allow_offers_default`.
- `StorePolicy` lets users manage only their own store. `ListingPolicy` allows creation only for confirmed, non-banned users with a non-suspended store; edit/update/destroy are owner-only until the admin panel exists. Owners delete drafts; every other state is archived.
- The seller listings index is `GET /sell` (`Sell::ListingsController#index`). `Sell::ListingCollection` owns the tab/status mapping (active = published + reserved; pending_review, drafts, rejected, sold, archived), the single grouped status COUNT for the tab badges, the case-insensitive title filter (`ILIKE` + `sanitize_sql_like`) and Pagy pagination at 20 per page. Invalid tabs fall back to active and invalid pages clamp to the last page. The index renders a desktop table and mobile cards, with thumbnail (`:thumb`), price, status badge, views, favourites, updated date and archive/republish/delete-draft actions; checkboxes sit outside the bulk form via the HTML `form` attribute and the `bulk_select` Stimulus controller only drives select-all.
- Batch and state-transition operations are separate RESTful resources: `POST /sell/bulk-archive` (`Sell::BulkArchivesController`, `Sell::BulkArchive`) and `POST /sell/:listing_id/republish` (`Sell::ListingRepublishesController`). `Sell::BulkArchive` scopes ids to `current_user.listings`, ignores other sellers and archives only records where `may_archive?`. `ListingPolicy#republish?` mirrors `update?` (owner-only); republish uses the existing `submit`/`published` flash copy and redirects to the index.
- Deleting a draft via `Sell::ListingsController#destroy` returns to the drafts tab, and archiving any other state returns to the archived tab. Sold listings expose no archive action because AASM does not allow it.
- The header and account menu point to the real store/listing entry points. "My listings" opens `sell_listings_path`; the admin panel entry opens `admin_root_path` for admins and moderators; the store dashboard, sales, orders, inbox and wishlist remain placeholders.
- The admin area lives under the optional locale scope at `/admin`: a singular dashboard and the RESTful `listing_reviews` resource at `/admin/moderation`. Flipper's UI stays at the locale-less `/admin/flipper` mount. `Admin::BaseController` uses the dedicated admin layout, Devise authentication and a staff check that raises `ActiveRecord::RecordNotFound` for non-staff accounts, so regular users see a 404 rather than a 403.
- The admin shell has its own sidebar and top bar (listing search, six-locale switcher, back-to-site link and account menu) and deliberately omits the public header, footer and announcement bar. The sidebar lists every planned section, but only Dashboard, Moderation queue and Feature flags link anywhere; the rest render as disabled "coming soon" rows.
- `Admin::DashboardStats` caches the dashboard COUNT metrics for 60 seconds under `admin/dashboard/stats`. The dashboard table shows the ten oldest pending listings (`submitted_at ASC NULLS LAST, id ASC`).
- The moderation queue is owned by `Admin::ModerationQueue`: pending-only, category-descendant, seller-kind, photo-EXISTS and title filters, Pagy at 20 per page, the category options, the applied filters and the oldest/next/previous lookups used by the dashboard and review page. `Admin::SellerProfile` supplies account age, previous rejected moderations and the store's verified flag, batching rejection counts for the index.
- Admin policies subclass `Admin::ApplicationPolicy`: dashboard and listing moderation are available to staff, while the future user and setting screens are admin-only placeholders. The moderation controller authorises through `Admin::ListingPolicy`.
- `Listings::Moderate` performs the pending check, AASM transition and moderation log inside `listing.with_lock`; a second moderator receives `nil` with no duplicate log or email. Emails are enqueued only after the lock transaction returns successfully.
- `ListingModeration::REJECTION_REASONS` lists the eight predefined reasons. `ListingModeration.compose_reason` translates the selected code in the seller's locale and joins it to the optional note with an em dash; the combined text is stored on both `listings.rejection_reason` and `listing_moderations.reason`.
- `ListingMailer#approved`/`#rejected` render HTML and text in the seller's locale through `I18n.with_locale`, pass the locale explicitly to listing/edit URLs and use the inline-styled `listing_mailer` layout. The dashboard/review UI uses the `moderation_shortcuts` Stimulus controller (A, R, J/K) and ignores keys while typing.
- The cart is a `Cart` owned by a user or by a guest `token` stored in the signed `cart_token` cookie. Guest carts exist only while Flipper `:guest_checkout` is enabled and are merged into the user cart by `Carts::Merge` on the first signed-in request. `CartItem` enforces unique `[cart_id, listing_id]` pairs and the purchase rules (own listing, visibility, vacation mode, stock).
- `Carts::AddItem` owns every add-to-cart rule and returns translated errors; `Cart#cached_item_count` backs the header badge and is invalidated by `CartItem belongs_to :cart, touch: true`.
- A checkout is one `Checkout` (payment group) split into one `Order` per store. `Checkouts::Start` locks the cart, validates the address/terms, reserves stock, writes order line snapshots and calls the payment gateway; the controller then calls `Checkouts::Complete`, `Fail` or the expiry job. Orders are idempotent through status guards and `checkouts.idempotency_key`.
- Stock reservation uses `Listing#reserve_stock!` inside `with_lock` (SELECT FOR UPDATE): `Checkouts::Start` first locks every cart listing in one `ORDER BY listings.id` query, then individual stores move `published → reserved` via AASM, while business stores decrement `quantity` atomically and also reserve when the last unit goes. `Listing.visible` additionally requires `quantity > 0`. `release_stock!` restocks (release when quantity is back above zero, including sold → published), `mark_sold_after_sale!` marks the lines sold on payment. Reservations last 15 minutes (`Checkout::RESERVATION_WINDOW`).
- `ReleaseExpiredReservationsJob` is scheduled every minute from `config/recurring.yml` for development, test and production. `AutoCompleteOrderJob` completes delivered orders when the buyer-protection window (`Setting buyer_protection_days`) ends.
- `Payments.gateway` is the single payment boundary. Test and key-less development environments use `Payments::FakeGateway` (deterministic success/failure, no Stripe account needed); any environment with both Stripe keys uses `Payments::StripeGateway`; production without keys raises `Payments::ConfigurationError`. `Payments.fake_gateway?` drives the test-payment copy and the development-only test banner.
- Stripe checkout uses one PaymentIntent per checkout and the Payment Element. `Checkouts::Start` stores `payment_intent_id` and `payment_client_secret`; a pending checkout with a client secret redirects to `checkout#show` instead of completing immediately, where `stripe_payment_controller.js` mounts the element and confirms the payment. Stripe.js is only loaded on that page via `content_for :head`.
- Webhooks are signature-verified at the locale-less `/webhooks/stripe`, stored in `webhook_events` (unique provider/event pair), and processed asynchronously by `StripeWebhookJob` → `Webhooks::ProcessStripeEvent`. Handled events: payment succeeded/failed, refunds, disputes, Connect account updates and Connect transfers. Duplicate deliveries are acknowledged without enqueuing a second job; processing errors are stored on the row and re-raised without setting `processed_at`.
- Stripe Connect uses Express accounts for every seller. `Payments::ConnectOnboarding` creates the account (`country: ES`, `business_type` company/individual, transfers capability) and an account-onboarding link; `Store::PaymentsController` owns the singular `/store/payment` page with payout status and requirements. Until `store.payouts_ready?` is true (or the fake gateway is active), carts reject the seller's listings.
- `Payouts::TransferToSeller` creates one `Payout` per completed order and transfers `total - commission` to the seller's connected account with an idempotency key; transfer failures are recorded on the payout and never roll back the order completion. Refunds go through `Payments.gateway.refund` per order, and disputes open the order state and email every admin.
- The CSP initializer is intentionally left unconfigured in this phase. If a CSP is added later, `https://js.stripe.com` must be allowed for the Payment Element.

- Order status is an AASM state machine on `orders.status`: `pending_payment → paid → shipped → delivered → completed`, plus `cancelled`, `refunded` and `disputed`. Shipping orders require carrier + tracking; local pickup orders do not. `Orders::Cancel` refunds when already paid and restocks; `Orders::ConfirmDelivery` opens the protection window and schedules auto-completion.
- `Order#commission_cents` is frozen at checkout as `subtotal × Setting commission_percent / 100` only when Flipper `:commissions` and `Setting commission_enabled` are both on; otherwise zero.
- `Address` stores a `region` and validates ES postal codes as five digits whose first two digits match the province prefix (`Address::PROVINCE_PREFIXES`). The checkout freezes the shipping address into `checkouts.shipping_address` JSONB.
- Order numbers are generated after insert from the primary key (`PCM-YYYY-NNNNNN`), which keeps them unique without a custom sequence. `OrderItem` snapshots title, unit price, shipping, seller name, photo URL and specs.
- The purchase UI is split into the basket (`/cart`), checkout form and confirmation (`/checkout/new`, `/checkout`), buyer orders (`/orders`) and seller sales (`/sell/sales`). Buy now adds the listing and carries `buy_now_listing_id` into the checkout so only that line is purchased; completion removes only purchased lines from the basket. State transitions are separate singular RESTful resources (`/orders/:order_id/delivery_confirmation`, `cancellation`, `problem_report` and the seller equivalents).
- `OrderMailer` renders buyer confirmation, seller new sale, shipped, delivery confirmed and cancelled emails as HTML + text in the recipient's locale and enqueues them with `deliver_later`.
- Favourites, follows, saved searches and notifications are persisted through `favourites` (unique user/listing; `listings.favorites_count` counter cache), `follows` (unique follower/store; `stores.followers_count`), `saved_searches` (normalised jsonb filters, frequency, email alerts), `notifications` (polymorphic notifiable, jsonb params, read timestamp) and `notification_preferences` (unique user/kind with in-app/email flags).
- `ListingSearch.normalized_params` is the single category-aware whitelist used by both filtering and saved searches; `ListingSearch.normalize_params` never raises on malformed input. `suggested_name` builds a six-part human name (category, specs, tags, condition, region, query, price last) for the save-search UI.
- `SavedSearch#matches?` ANDs the category subtree, price range, condition, specs, tag slugs, region, free shipping and full-text query. `SavedSearches::Matcher` prefilters category and jsonb price in SQL, then evaluates candidates in Ruby; `SavedSearches::Digester` groups due daily/weekly searches into one email per user and advances `last_notified_at` even for empty runs.
- `Notifications.record` is the single data-only notification entry point (never stores rendered text) and honours `NotificationPreference`; in-app rows invalidate the cached unread count and broadcast `shared/notifications_bell` when that partial exists.
- `EmailUnsubscribe` signs 90-day one-click tokens carrying `user_id`, `saved_search_id` and `kind`; `AlertMailer` emits locale-aware price-drop, followed-store, saved-search match and digest emails with the `List-Unsubscribe` headers.
- Phase 5a UI lives on singular/restful resources: `/wishlist`, `/l/:listing_id/favourite`, `/stores/:store_id/follow`, `/account/saved_searches`, `/notifications`, `POST /notifications/read`, `/account/notifications` and `/unsubscribe`. `Wishlist` owns the tab/count queries and `NotificationInbox` owns the unread/all filter plus 20-per-page Pagy pagination. `ApplicationHelper` memoises favourite/follow ids once per request; the listing-card fragment caches only the presentational card (keyed by listing, locale and eager state) and the favourite button renders fresh outside the cache so no CSRF token is shared. The notification bell is rendered from `shared/_notifications_bell` with an explicit locale so Turbo broadcasts from jobs keep the recipient's language.
- Chat is a `Conversation` between a buyer and a seller (optionally tied to one listing, otherwise store-level) with per-side unread counters, archive flags and `last_message_at`; `Conversation.for_user`/`visible_for` own inbox visibility. `Messages` are text/system/offer events; system and offer events store an I18n key in `body` plus interpolation data in `metadata`, so both participants read them in their own locale. Commit hooks update the recipient counter, append to the `conversation` Turbo Stream and record a `new_message` notification; `Messages::EmailNotificationJob` waits 10 minutes and only emails when the message is still unread and the recipient allows email.
- `Messages::SafetyScanner` flags phone numbers, emails, IBANs and multilingual off-platform payment terms without blocking the message; flagged messages render a translated Buyer Protection warning to the recipient. Model validations enforce 30 text messages per sender per 10 minutes and 10 new conversations per buyer per hour with translated errors.
- Offers are gated by Flipper `:offers` (controllers raise 404 and every offer UI block is hidden when off). `Offers::Create` finds/creates the conversation and posts an offer event; `Offers::Respond` owns accept/decline/counter transitions and notifications; `Offers::Expire` + `Offers::ExpiryJob` (every 15 minutes) expire overdue offers and remind about offers expiring within 6 hours. Accepted offers are redeemable only by the buyer, before expiry and for the same listing; `cart_items.offer_id` + `unit_price_cents` freeze the accepted price through checkout and order snapshots.
- `Block` is a unique directed pair; `Block.between?` is the single block check used by conversations, messages and offers. Each side can block/unblock from the conversation, listing seller card or storefront, and the inbox “Blocked users” tab lists and removes blocks.
- Reports implement DSA notice-and-action: optional reporter with a contact email for anonymous notices, polymorphic `reportable` (Listing/Store/Message/User), ten reason codes, a 20–2000 character statement, open/in_review/actioned/dismissed status and a handler/resolution note. `Reports::Submit` validates and acknowledges by email; `Admin::ResolveReport` dismisses or applies the type-specific action (archive listing, suspend store, hide message, ban user) and emails the translated statement of reasons.
- Public storefronts live at `/s/:slug` (`StorefrontsController#show`, routed as `resources :stores, only: :show`) and expose the seller card, visible listings, message-seller/block controls and the store report link.
- Phase 6 adds `Review` (one per order, buyer-only, delivered/completed within 60 days, editable for 7 days, one seller reply, visible/hidden status). `Review` validates eligibility in the model and refreshes `stores.rating_average`/`ratings_count` in `after_commit` with one aggregate query. Reviews are reportable and admin action hides them.
- `ListingView` is a daily `(listing_id, date, views)` rollup written with `INSERT ... ON CONFLICT DO UPDATE views = views + 1` from the existing listing view counter, so `Sell::Analytics` reads a small table instead of scanning listings.
- `Sell::Analytics` (app/queries) owns every dashboard metric: revenue, orders, units, AOV, views, conversion, favourites, followers, daily revenue series and top listings, plus pending counts. Results are cached for 10 minutes per store, range and store update timestamp. The dashboard uses an inline SVG chart with an accessible data table.
- Public storefront tabs are `listings` (store-scoped `ListingSearch`, separate recently sold section), `about` (description, policies, legal/trader block for business stores) and `reviews` (distribution, Pagy, sort). Store header/about/review fragments are cached; SEO uses MetaTags plus Organization/Person JSON-LD with `aggregateRating`.
- Vacation mode adds `stores.vacation_until`; `Stores::VacationAutoOffJob` is scheduled for the return date and re-checks the stored date before switching mode off.
- Account settings use the `/account` namespace: profile/security (`/account/profile`), addresses, notification preferences, privacy and signed data-export downloads. Deletion (`Accounts::Delete`) requires password or typed username for OAuth accounts, blocks paid/shipped orders, soft-deletes/anonymises the user, purges the avatar and archives listings while keeping orders/reviews for retention.
- Admins/reviewers: policy objects are `ReviewPolicy`, `AccountPolicy`, `AddressPolicy` and `Sell::DashboardPolicy`. All Phase 6 copy lives in `config/locales/phase6.*.yml` with the same nested structure as the existing locale files.
- Phase 7a adds the staff management screens under `/admin`: listings (filters, sortable tables, CSV, bulk approve/reject/archive/label/feature, full editor reusing the wizard fields, permanent deletion limited to drafts/archived listings without orders), users (staff-readable, admin-mutated: role changes with self-demotion and last-admin guards, ban/unban, confirmation/password-reset emails, soft delete, impersonation), stores (verify/unverify, suspend/reactivate, review visibility, edit), orders (ship/deliver/complete/cancel/refund/dispute/notes), payouts (retry) and the audit log.

Controllers only render; business rules live in `Admin::BanUser`, `Admin::ChangeUserRole`, `Admin::SuspendStore`, `Admin::BulkListingAction`, `Admin::ShipOrder`, `Admin::DeliverOrder`, `Admin::CancelOrder`, `Admin::PartialRefund`, `Admin::ResolveDispute` or the existing services (moderation, account deletion, payouts).
- `AdminAuditLog` stores every staff mutation (actor, action, polymorphic auditable, JSONB change payload, IP, user agent) through the `Admin::Auditable` controller concern. The column is `changes_data` because Active Record reserves `changes`; the model exposes `changes`/`changes=`.
- `OrderNote` holds staff-only internal order notes. Order now has a `resolve` AASM transition (`disputed → completed`) used by the dispute-release action. Partial refunds pass an explicit amount to `Payments::Gateway#refund`.
- Impersonation signs the admin in as the target user and keeps `session[:impersonator_id]`; a persistent banner offers a stop button. Impersonated sessions receive a 404 in the admin area and are redirected away from payment settings. Start/stop are audit-logged and admins cannot impersonate admins or themselves.
- `Accounts::Delete` archives with model callbacks and recomputes affected store/category counters after the transaction; legacy rows that no longer satisfy validation are archived through `Listing#archive_without_validation!` so the counter callbacks still run. The signed GDPR export download now requires the signed-in owner in addition to the signed token.
- All Phase 7a copy lives in `config/locales/phase7.*.yml`; dynamic status/role/action prefixes are ignored by i18n-tasks.
- Phase 7b adds the catalogue and platform configuration area under `/admin`. Every new screen is admin-only: the new controllers inherit `Admin::AdminOnlyController`, which returns 404 for moderators, and their policies only allow admins. Every mutation is audit-logged through `Admin::Auditable`.
- `BlocksImpersonation` is the single guard for impersonated sessions outside the admin area. It blocks account deletion, password changes, email/profile updates, GDPR export creation/download and seller payout settings, redirecting back with a translated alert. `Store::PaymentsController` reuses it with its existing payout-specific message.
- `TranslatableFieldsHelper#translatable_form_field` (partial `admin/shared/_translatable_fields`) renders Mobility jsonb attributes as six tabs (ES first, EN/FR/DE/IT/PT) with a missing-translation dot. Spanish is required; other locales are optional and use the configured fallbacks. It powers category, attribute-definition, attribute-option and tag forms.
- Category administration keeps the FriendlyId slug history, exposes editable slugs and shows direct/total listing counts. The tree view uses the shared `sortable` controller; `PATCH /admin/category_positions` (with `ordered_ids` and optional `moves`) reorders siblings and moves categories while `Category` validations prevent cycles. Deleting is allowed only when the category has no listings or children. Category attribute links touch the category after commit so the navigation and descendant caches invalidate.
- `CategoryAttribute` administration shows effective (own + inherited) filters, links inherited rows to the ancestor, and lets admins add/remove/reorder own rows and toggle `required`. `AttributeDefinition` keys and used option values are immutable, input types are locked once listings use a definition, and deleting is blocked when used. `AttributeOptions::Merge` rewrites scalar and array jsonb specs in one SQL UPDATE and deletes the merged option; `Admin::AttributeUsage` counts option usage in one grouped query; `AttributeOptions::Import` supports one-value-per-line bulk adds.
- Tags remain split into staff-assigned product labels and seller tags. The admin screen supports translated names, colour-token preview, position/order changes, activation and listing usage counts.
- Country launch readiness is enforced in `Country#activation_requirements_met`: all legal kinds must be published in the country's default locale and at least one region must exist. `Country#launch_checks` drives the admin checklist and missing-reason copy. Regions are CRUD-managed and can be bulk-imported from `code,name` lines via `Regions::Import`; `db/seeds/regions.rb` seeds FR (13), GB (4 nations), DE (16), IT (20) and PT (20).
- `Listing.visible` now also requires `country_code` to belong to the cached `Country.launched_codes` and the category to be active, so deactivating a country hides its listings and `Listing`'s existing country validation blocks new ones.
- `Setting` values now validate both their declared type and key-specific ranges (commission 0–50, images 1–30, protection 0–90). `Admin::SettingsController` renders the grouped boolean/integer/decimal/string/text form and persists through `Settings::Update` in one transaction. The seed groups are general, listings, commissions, featured, buyer_protection, emails and maintenance.
- Maintenance mode is enforced by `ApplicationController#enforce_maintenance_mode`: non-staff visitors receive a translated 503 maintenance layout with `Retry-After: 3600`, while staff keep browsing; Devise routes, `/up` and the locale-less webhooks stay reachable.
- `FeatureFlag` stores the metadata row (key and description key) for each Flipper feature, seeded with translations. `/admin/features` lists every Flipper feature with an on/off toggle and percentage-of-actors rollout; `/admin/flipper` remains mounted for power users (linked from the sidebar and the features page).

## Listing state machine (AASM on `listings.status`)

```
                         submit (approval ON)          approve
   draft ────────────────────▶ pending_review ─────────────────▶ published
     ▲                              │                              │  ▲
     │                              │ reject(reason)                │  │ release
     │                              ▼                              │  │
     │                          rejected ────── submit ────────────┘  │
     │                                                  reserve        │
     │                                            published ─────────▶ reserved
     │                                                                    │
     │                                                       mark_sold  │
     ├────────────────────────── archive (any state except sold) ◀────────┤
     │                                                                    ▼
   archived ─────── republish ──────▶ pending_review (approval ON)         sold
                              └──────▶ published (approval OFF)

   submit from draft/rejected and republish from archived publish DIRECTLY
   when Setting.get(:listings_require_approval) is false.

   Material edit of a published listing (title, description, specs, category,
   or a photo add/remove) ─────▶ pending_review (only when approval is ON).
   Price / quantity / shipping edits leave the listing published.
```

## Stripe configuration
- Keys are read from `Rails.application.credentials.dig(:stripe, :secret_key/:publishable_key/:webhook_secret)` first and then from `STRIPE_SECRET_KEY`, `STRIPE_PUBLISHABLE_KEY` and `STRIPE_WEBHOOK_SECRET`.
- `Payments.stripe_configured?` requires both the secret and publishable keys. With them present, `Payments.gateway` returns `Payments::StripeGateway` in development and production; test always uses `Payments::FakeGateway`. Production without both keys raises `Payments::ConfigurationError`.
- `config/initializers/stripe.rb` sets `Stripe.api_key` after boot and after code reloads when the secret key exists.
- Local webhook testing: run `stripe listen --forward-to localhost:3000/webhooks/stripe` and put the printed `whsec_…` value in credentials or `STRIPE_WEBHOOK_SECRET`. The endpoint lives outside the locale scope and verifies `Stripe-Signature` before storing anything.
- Sellers complete Connect onboarding at `/store/payment`; Stripe redirects them back to the same page. `account.updated` webhooks keep the store's payout flags and requirements in sync.
- The CSP initializer (`config/initializers/content_security_policy.rb`) is deliberately left unconfigured in this phase. If one is added, allow `https://js.stripe.com` for the Payment Element script.
